# PWDTWO — Feature Research and Accepted Additions

Research date: 2026-10-08.

Status: R01–R12 accepted into the functional scope on 2026-10-08, then revised the same day to remove trusted-contact emergency access and expiring sharing links. PWDTWO-managed device approval and revocation were also removed; setup uses provider authorization and vault unlocking. Deliberate sharing remains accepted. Subsequent multiple-vault, cloud-file synchronization, and long-notes requirements are also recorded in specifications.md, with KDBX as a conditional format preference. Priorities and implementation phases will be decided later.

This comparison focuses on features useful for a personal password manager across macOS, iPhone, iPad, and Android. It uses official product and support documentation. Feature availability can differ by platform and subscription; an unverified feature is not treated as absent.

The initial 13 stories cover device applications, search, saving logins, password generation, browser and mobile-app autofill, synchronization, offline operation, master-password and biometric unlocking, recovery keys, automatic locking, synchronization conflicts, and macOS-only imports from other password managers.

The accepted additions below extend that baseline with everyday credential management and modern sign-in methods. Their register order does not assign priority or an implementation sequence.

## Accepted feature register

R01–R12 are accepted with R12 revised to exclude trusted-contact emergency access and replace expiring links with encrypted copy transfer. R05/R10 are also revised to use provider security and local vault unlocking without PWDTWO-managed device approval or revocation. Their detailed functional stories are maintained in specifications.md; approved phase assignments are maintained in [tasks.md](tasks.md#approved-development-phases).

| ID | Accepted addition | User-visible outcome and scope details |
| --- | --- | --- |
| R01 | Browser save and update prompts | Offer to save a new login or update an existing one during website sign-up, sign-in, and password changes. Let the user confirm the correct account. Keep a way to recover a generated password if the website flow fails before the entry is saved. |
| R02 | Complete entry management, history, and trash | Support normal editing, deletion, undo, and recovery. Let users inspect an earlier password if a change failed, and restore accidentally deleted entries. Sync-conflict preservation and ordinary password history serve separate recovery needs. |
| R03 | Reliable manual access and account selection | Reveal/hide and copy credentials when autofill is unavailable; distinguish multiple accounts for one service; associate an entry with its legitimate website addresses. Define when the user chooses a login and what happens on a mismatched website. |
| R04 | Export and independent backup/restore | Let users leave the application with their data and restore a vault after data loss using a portable encrypted backup. Support optional scheduled encrypted backups, disabled by default with frequency controlled by the user in Settings. Maintain one shared backup configuration and exactly one application-managed backup per vault, synchronized across devices, with one user-selected device creating scheduled backups. Each successful backup replaces the previous one; no application-managed backup history is retained. Support manual encrypted backup exports, including entries, attachments, history, trash, and required recovery metadata; restore into a separate vault by default. Bulk export for migration to another password manager is macOS-only, with format-dependent coverage disclosed to the user. This accepted requirement does not imply that both competitors' ordinary exports are encrypted. The recovery key does not recreate a lost vault. |
| R05 | Device setup, activity, and sync status | Guide vault creation and opening on additional devices using provider authorization and vault credentials. Show informational device activity, pending changes, last successful sync, and errors. Cloud-account/device access is managed through provider/OS controls; PWDTWO does not remotely revoke access to downloaded vaults. |
| R06 | Passkeys | Create, save, synchronize, and use passkeys for supported websites/apps alongside passwords. Define creation, use, and migration separately; password CSV import cannot be assumed to migrate passkeys. |
| R07 | Built-in authenticator codes | Scan a setup QR code or enter a setup key, then generate and copy/fill the account's verification code. Keeping both password and code in one vault combines them behind the same vault access; users may continue using a separate authenticator for selected accounts. |
| R08 | Password-health and exposure checks | Provide weak/reused-password detection, free leaked-password checks, and an actionable list. Use opt-in HIBP Pwned Passwords hash-prefix checks, disabled by default. Email-address/account breach monitoring and paid monitoring subscriptions were excluded by the user on 2026-10-09. Provide manual checks and optional checks on a user-configured schedule, running only when online and the relevant vault is unlocked. Notifications use generic text; delivery preferences remain to be decided. The vendors' differently named monitoring features should not be treated as identical. |
| R09 | Favorites, tags, notes, and custom fields | Favorites and simple tags aid navigation; notes and extra fields can retain account numbers, security-question answers, or recovery codes. Preserve useful imported information beyond website/username/password according to the supported migration rules. |
| R10 | Provider security and local vault unlocking | Revised scope: no separate PWDTWO account, managed enrollment, or existing-device approval. Use any required provider authorization followed by vault-password unlocking or recovery; optional biometrics remain device-local. Provider MFA remains the provider's responsibility. |
| R11 | Mac application autofill and passphrases | Extend Mac autofill beyond browsers, and offer memorable multiword passwords alongside the existing character-based generator. |
| R12 | Sharing, cards, and attachments | Support shared family logins through shared vaults and encrypted individual copy transfers, cards, identity forms, and document attachments. Both sender and recipient must have compatible PWDTWO applications; browser-only access is excluded. Individual shares deliver independent copies; ongoing updates synchronize through shared vaults. Each individual transfer uses an encrypted file and a generated transfer password communicated separately; copies have no collection deadline, expiration, or remote revocation. Shared-vault participants have equal access to contents, without PWDTWO owner/editor/viewer roles; the cloud provider controls remote file access and management. Trusted-contact emergency access has been removed by the user. |

Feature approval covers every register entry as revised above. The user subsequently approved the phased implementation baseline on 2026-10-09; see [tasks.md](tasks.md#approved-development-phases).

## Supporting details captured in the functional requirements

- Explicit autofill behavior includes account/site selection and user interaction before filling credentials. These details are captured alongside website matching in the functional stories. [Autofill security](https://support.1password.com/browser-autofill-security/), [website matching](https://support.1password.com/autofill-behavior/).
- Recoverable generated-password history addresses a common failure case: a password is generated or changed but the website flow is interrupted. 1Password documents this separately from saved item history. [Recover a generated password](https://support.1password.com/recover-unsaved-password/).

## Additional vault requirements and format feasibility

Assessment date: 2026-10-08. “KeyPass” is interpreted as KeePass's KDBX format. The user corrected “watch” to “vault”; credit cards and secure notes remain vault contents.

| Addition | Specification |
| --- | --- |
| Multiple independent vaults, each with its own password | Story 40; unlocking, recovery, setup, search, autofill, and backup stories now identify the relevant vault. |
| Synchronization of encrypted vault files through iCloud Drive and Google Drive | Story 41: iCloud Drive on macOS, iPhone, and iPad; Google Drive on macOS, iPhone, iPad, and Android. One cloud provider per synchronized vault; local-only vaults are also supported (story 45). Users can migrate between storage modes/providers (story 46). Simultaneous multi-provider synchronization is excluded. |
| KeePass-compatible vault files if there are no major limitations | Conditional story 42. The user confirmed PWDTWO as the primary application; full compatibility with other KeePass solutions is unnecessary. Evaluate KDBX with PWDTWO extensions; final format adoption remains pending technical assessment. |
| Credit cards and secure notes in each vault | Stories 30, 38, and 40. |
| Dedicated long-text notes on every password and credit card | Story 43, referenced from the existing entry stories. |

KDBX fits the core vault records well, but significant tradeoffs exist against the full accepted feature set. The following separates documented capabilities from architectural conclusions; it is not a final storage design.

| Area | Evidence and consequence |
| --- | --- |
| Independent vaults | Each KeePass database has its own master key. Separate files naturally support independently protected vaults. [KeePass master keys](https://keepass.info/help/base/keys.html). |
| Notes and structured data | Standard entries include notes, and entries support custom string fields. The schema also describes groups, tags, history, and binary data. Long multiline notes fit the format; practical size limits still depend on clients. Cards and identities can use custom fields, but a generic reader may not recognize this application's templates or form-filling behavior. [Entry fields](https://keepass.info/help/v2/entry.html), [KDBX schema](https://keepass.info/help/download/KDBX_XML.xsd). |
| Attachments and history | KDBX supports encrypted binary attachments; KeePass supports earlier entry versions. Embedding large documents enlarges the vault file, so file size and offline availability need evaluation. Independent per-attachment downloads would require further design if desired. [KDBX format](https://keepass.info/help/kb/kdbx.html), [entry history](https://keepass.info/help/v2/entry.html#hst). |
| Recovery key | KeePass combines all configured key components. A password and key file are both required when both are configured. This does not implement our alternative recovery key that works when the password is forgotten. Additional recovery machinery would be needed, and its effect on ordinary KDBX interoperability must be evaluated. [Master keys](https://keepass.info/help/base/keys.html), [key derivation](https://keepass.info/help/kb/kdbx.html#keys). |
| Sharing and access controls | KeePass has no per-entry or group access-control lists. KeeShare can exchange selected groups through separate containers, but retained copies remain available. PWDTWO excludes internal roles and per-entry permissions for shared vaults; participants have equal access to contents. Expiring invitations are excluded. Removal of future provider access is governed by provider permissions and cannot erase retained copies; secure sharing of unlocking credentials still needs a concrete design. [KeePass multiple users](https://keepass.info/help/base/multiuser.html), [KeeShare](https://keepassxc.org/docs/KeePassXC_UserGuide#_database_sharing_with_keeshare). |
| Passkeys and authenticator codes | KeePassXC supports TOTP and stores passkey material in additional entry attributes. This demonstrates that KDBX can carry the data; it does not establish uniform semantics across clients or support for all mobile autofill/passkey surfaces. Interoperability must be tested with selected clients and field conventions. [KeePassXC guide](https://keepassxc.org/docs/KeePassXC_GettingStarted), [upstream passkey documentation](https://raw.githubusercontent.com/keepassxreboot/keepassxc/develop/docs/topics/Passkeys.adoc). |
| Conflict preservation | KeePass synchronization normally chooses a current entry using modification times and keeps other changes in history, subject to history retention. Our accepted behavior preserves unresolved versions until the user chooses. We must implement that behavior explicitly and examine interactions with other clients. [KeePass synchronization](https://keepass.info/help/v2/sync.html). |

For cloud synchronization, the confirmed product scope and documented integration routes are:

| Provider/topic | Supported path and remaining limits |
| --- | --- |
| iCloud Drive | Required on macOS, iPhone, and iPad. Apple documents iCloud Documents for synchronizing files and access through the Files/document-provider system on Apple devices. A file may need downloading before it is available offline. [Apple storage guidance](https://developer.apple.com/documentation/cloudkit/deciding-whether-cloudkit-is-right-for-your-app), [document synchronization](https://developer.apple.com/documentation/uikit/synchronizing-documents-in-the-icloud-environment). |
| Google Drive | Required on macOS, iPhone, iPad, and Android, providing synchronization for vaults used across Apple and Android devices. The Drive REST API supports file storage and authorization flows for installed applications, providing a documented integration route subject to implementation and testing. [Drive API](https://developers.google.com/workspace/drive/api/guides/about-sdk), [native-app authorization](https://developers.google.com/identity/protocols/oauth2/native-app). |
| Concurrent updates and retention | A provider's change feed or file versions are not entry-level vault merging. Google Drive may purge ordinary old revisions. Provider history therefore cannot alone satisfy our unresolved-conflict, entry-history, or independent-backup requirements. [Drive changes](https://developers.google.com/workspace/drive/api/guides/about-changes), [Drive revisions](https://developers.google.com/workspace/drive/api/guides/manage-revisions). |
| File location and access | Google distinguishes user-selected files from hidden application storage; hidden app-data files cannot be shared. The storage location must be selected deliberately to fit portable vault files and sharing. [Drive access scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [app-data restrictions](https://developers.google.com/workspace/drive/api/guides/appdata). |

The user confirmed that Google Drive covers Android and synchronization across Apple and Android devices. iCloud Drive integration on Android is not required and is not a feasibility blocker. The user confirmed local-only vaults as an option, with one cloud provider per vault when synchronization is enabled. Different vaults may use different providers, but the same vault does not synchronize simultaneously through both.

KDBX remains a preferred candidate rather than an unconditional format decision. Recovery, granular access controls, and conflict handling are substantial enough that “no major limitations” has not been established. Any proposal to use additional metadata/services, restrict interoperability, or change an accepted feature must make that tradeoff explicit before the format decision is finalized.
